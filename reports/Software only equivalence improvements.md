# Pin the cameras, then propagate every lag

With the two phone videos and the FBX frozen, the best software lever is the camera calibration, not synchronisation or statistics. In both takes the self-calibration drives the iPhone 17 focal length to **1.5–2.1 times its metadata value**. After's 1080p side view was fitted at 2208 px and then 2852 px, and Action's 1080p front view at 3045 px when the focal was left free. The lens tag (26 mm equivalent) implies about **1442 px**, and Apple's stabilisation crop could plausibly raise that to about 1800 px. Two cameras aimed at one person are the textbook singular case for estimating two unknown focals ([Kocur et al., CVPR 2024](https://arxiv.org/html/2311.16304)). The current ±15% prior is a single residual set against roughly 3,600–5,400 reprojection residuals, so it cannot stop the drift. The recommended order follows from that. First build a blinding harness and extend the simulator. Next fix the time grid and interpolation (After triangulates on its 30 fps variable-frame-rate view), then pin the iPhone focal, free the 480p focal and take the hand point out of the calibration. After that, make the sync continuous and multi-signal, and draw both lags and the focal inside the Monte Carlo. Only then add precision upgrades: a dedicated hand model on full-resolution crops, and noise-weighted triangulation. Shoulder-point semantics come last, because they are the only change that alters the estimand. One timing worry can be closed now. Parsing the MP4 sample tables for this report showed that OpenCV's frame times **match the container timestamps exactly in all four videos**, with no video edit-list offset. Re-analysing After and Action with any of this code is **exploratory**, because both takes and their pass/fail pattern have been seen. The re-analysis must follow a blinded protocol, and the ±15° margin stays where it is.

## Container timing is sound, but After triangulates on the wrong clock

The cheapest worry to retire was frame timing, and it is retired. A check run for this report parsed each file's `stts`, `ctts` and `elst` boxes and compared the resulting presentation times with the `cv2.CAP_PROP_POS_MSEC` values that [`video_replicates.py`](../backend/app/validation/video_replicates.py) stores. The two agree to **0.000 ms in every frame of all four videos**. The iPhone files (1080×1920, 59.97 fps average, 16.67/18.33 ms ticks at a 600 Hz timescale) carry an edit list with a zero media time on the video track. The two 480p files (480×854, portrait) have no edit lists and genuinely variable intervals: **10.9–46.9 ms in After-Front and 14.7–52.1 ms in Action-Side**. This matters because tools disagree on how edit lists apply ([avidemux forum](https://avidemux.org/smif/index.php?msg=85672)), and stream headers can report a constant rate for a variable-rate file ([FFmpeg trac #10799](https://trac.ffmpeg.org/ticket/10799)). Neither problem affects these files. The check should still become a guard in code, a container-timestamp assertion at extraction, so that a future file with an edit-list offset is refused rather than silently mistimed.

The real timing defect is the choice of time grid. `reconstruct` and `evaluate_conditional` in [`multiview.py`](../backend/app/validation/multiview.py) and [`conditional_equivalence.py`](../backend/app/validation/conditional_equivalence.py) resample the second view onto **the first view's timestamps**. In After the first view is the 480p, ~30 fps variable-rate front phone, so the 60 fps iPhone is decimated and the analysis runs on an irregular grid. In Action the first view is the iPhone, which is already right. All resampling uses `np.interp`, which is linear. For a wrist moving sinusoidally at 3 Hz with 15 cm amplitude, linear interpolation errs by about **7 mm across a 33 ms gap and 18 mm across a 52 ms gap**. At 480p scale that is 3.5–9 px, as large as the keypoint noise itself. Cubic interpolation error scales with h⁴ rather than h² and is about ten times smaller at these gaps (in-house arithmetic, [synchronisation notes](../research_notes/Software%20only%20equivalence%20improvements/software_synchronisation.md)). The fix has three parts. First, always use the highest-rate constant-frame-rate view as the reference grid. Second, replace `_interpolate` with a shape-preserving cubic (PCHIP) or a smoothing spline evaluated at true timestamps. Third, apply the 6 Hz Butterworth only after resampling onto the uniform grid, since `filtfilt` on samples treated as evenly spaced distorts both timing and amplitude. The Monte Carlo should perturb the original variable-rate samples and then re-interpolate, so that interpolation smooths the noise the same way it smooths the data. RocSync showed what sub-frame interpolation buys: it cut 30 fps reprojection error from 3.07 to 1.02 px ([RocSync](https://arxiv.org/html/2511.14948v1)).

### Video-to-video lag should be continuous and carry a standard error

`refine_lag` already does the right kind of thing. It minimises moving-frame reprojection error around a coarse wrist-speed lag, the approach published sync methods take: model trajectories in continuous time and estimate the offset jointly with the geometry ([Albl et al., CVPR 2017](https://ar5iv.labs.arxiv.org/html/1704.06843); [Vo et al., spatiotemporal bundle adjustment](https://arxiv.org/pdf/2007.12806v1.pdf)). But it searches a **quarter-frame grid of the reference view**. On After's 30 fps grid that is a step of 8.3 ms, so quantisation alone allows ±4.2 ms. Within each step it uses linear interpolation, and it returns no uncertainty. Replace it with a bounded scalar minimiser (Brent) over the same robust cost, evaluated on spline-interpolated keypoints. The curvature of the cost at the minimum then gives a local standard error. A parametric bootstrap gives a better one, inflated for autocorrelation: add the measured keypoint noise and re-run the coarse and fine steps, so that a slip to the wrong correlation peak counts as error. Fit a clock-rate term only as a check. If |ρ − 1| times the take duration stays under about 2 ms, fix ρ = 1. For a wrist moving about 1000–1500 px/s in the 1080p view, 1 ms of lag error is about 1–1.5 px of disagreement, so averaging over hundreds of moving frames should localise the lag to a few milliseconds (in-house estimate, to be confirmed by simulation). The generic-scene method VisualSync reports 42–78 ms median errors on multi-person benchmarks ([VisualSync](https://arxiv.org/html/2512.02017v1)). That is a much harder setting, and its 0.1 ratio test for rejecting ambiguous cost landscapes is worth copying.

Audio is a useful cross-check but should not set the final lag. All four files have audio. GCC-PHAT is the standard tool for refining an already-coarse audio delay ([EUSIPCO 2015](https://new.eurasip.org/Proceedings/Eusipco/Eusipco2015/papers/1570096423.pdf)). But an audio lag equals the video lag plus the difference between the two files' internal audio-to-video offsets. The parse found that the iPhone's first audio track skips **2112 priming samples (44 ms at 48 kHz)** through its edit list, while the re-encoded 480p files have no edit list at all, so their priming compensation is unknown. On an iPhone 15 Pro, stabilisation has been reported to delay video by up to about a second relative to audio ([Apple Developer Forums](https://developer.apple.com/forums/thread/742022)). Use the audio lag only to confirm that the pose-based lag sits within about one frame of it, which rules out a cycle slip on repetitive signing. Do not use it to correct the pose-based lag.

### Video-to-FBX lag needs several signals that are not the tested angles

The FBX lag is currently a single cross-correlation of 3D wrist speed over the whole FBX clock, refined with a parabolic peak. The camera–IMU literature aligns streams with rotation-invariant signals such as angular-velocity norms ([USPTO 12361720](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12361720); [Qin & Shen](https://arxiv.org/pdf/1808.00692)). It also treats the offset as a parameter with its own covariance, because an uncorrected offset adds error the model does not account for ([Li & Mourikis, IJRR 2014](https://intra.ece.ucr.edu/~mourikis/papers/Li2014IJRR_timing.pdf)). The Rokoko FBX is a fused skeleton, not raw gyro data, so both sides should derive the same quantities: forearm and upper-arm angular-velocity norms (the rate of change of the unit segment vectors), plus knuckle-centre and wrist linear speed. Estimate a lag from each signal and restrict every correlation to the FBX sign window plus margins. Reject any estimate whose second peak comes within 10% of the first, and combine the rest with a weighted median. The spread across signals is a non-circular standard error. **No signal may be one of the nine tested angles or its derivative.** Elbow-angle rate, which the project has used as a cross-check, partly aligns the very quantity under test, so it stays a sensitivity check only. Expect 5–15 ms here (in-house), consistent with the roughly 8 ms agreement seen between wrist speed and elbow rate. Published wearable-to-video figures are far coarser: SyncWISE reaches 90% within 700 ms on free-living video ([SyncWISE](https://experts.illinois.edu/en/publications/syncwise-window-induced-shift-estimation-for-synchronization-of-v/)). IMU-to-IMU alignment on impulsive actions reaches 4.8 ms ([TU Wien thesis](https://repositum.tuwien.at/handle/20.500.12708/226907)). The stakes are concrete: a 10 ms lag error on an elbow moving at 300°/s gives up to 3° of instantaneous difference, perhaps 1–2° of RMS. Against a pass threshold of about 9° true RMS, that cannot be ignored.

## The iPhone focal runs to twice its lens value, and the prior cannot stop it

The calibration diagnostics in the saved reports make the problem plain. `calibrate_pairs` starts both cameras at 28 mm converted along the diagonal (1425 px for the iPhone, 634 px for the 480p view) and frees both focals under a log-normal prior with SD 0.15. In After it returned **2208 px, then 2852 px** for the iPhone once the hand point changed. The baseline moved from 56.1° to 64.8°, and the right-elbow upper bound moved from 8.0° to 14.4° ([sequential testing report](Single%20take%20equivalence%20sequential%20testing.md)). Action's focal-free run returned **3045 px**, 5.1 prior SDs from the start value. The prior does not hold because of how it enters the fit. `PRIOR_PX · log(f)/0.15` is one residual next to 4 × 890 (After) or 4 × 1350 (Action) reprojection residuals and the heavily weighted bone-length terms, all treated as independent although frames are strongly autocorrelated. Any small systematic gain in fit from moving toward a weak-perspective solution outweighs it. That behaviour is what geometry predicts. Kocur and colleagues show that focal estimation from two views is singular when the principal axes intersect, as they do when both phones aim at the signer. With **one** unknown focal, the degenerate case shrinks to the calibrated camera's centre lying on the other camera's optical axis, which a 50–65° yaw rules out ([Kocur et al.](https://arxiv.org/html/2311.16304)). CasCalib's authors skipped two-view bundle adjustment because noisy keypoints leave it under-constrained, and still saw about 11% single-view focal error ([CasCalib](https://arxiv.org/html/2405.06845v1)).

The software fix is to stop estimating the iPhone focal from the body. Apple's "26 mm equivalent" refers to the 4:3 still frame. Converting along the 4:3 width (34.62 mm), not the 16:9 diagonal, gives a horizontal field of view of 67.3°, close to the 67.1° forum report for a 13 Pro Max ([Apple forum 714978](https://origin-devforums.apple.com/forums/thread/714978)), and **fx ≈ 1442 px** for 1920 px on the long axis (in-house arithmetic, [calibration notes](../research_notes/Software%20only%20equivalence%20improvements/calibration_from_existing_videos.md)). Two cautions apply. Typing 26 into the existing diagonal formula in `focal_from_35mm` would land 8% short. And Apple's standard stabilisation crops the field of view by an unpublished amount ([AVCaptureVideoStabilizationMode](https://developer.apple.com/documentation/avfoundation/avcapturevideostabilizationmode.md)), so a crop of 0–20% puts the true value somewhere in 1442–1800 px. Implement this as hard bounds on the iPhone log-focal in `least_squares`, or as a prior whose weight is scaled to the effective number of frames, not as another unit-weight residual. Leave the 480p focal free, because a messaging-app re-encode may have cropped or rescaled that frame and no 35 mm value can be assumed for it. Production pipelines make the same choice: OpenCap keeps per-device intrinsics measured offline, and Pose2Sim takes intrinsics from a board and estimates only extrinsics ([OpenCap intrinsics](https://github.com/stanfordnmbl/opencap-core/tree/main/CameraIntrinsics); [Pose2Sim](https://github.com/perfanalytics/pose2sim)). Action's exploratory runs already held the iPhone at 1425 px, within 1.2% of the metadata value. Its outstanding issue is the opposite one: the 480p focal was fixed at an arbitrary 634 px.

### Four supporting changes make the calibration independent of what is tested

First, take the hand point out of the calibration. `BONES` includes the wrist→knuckle segments, which is how a change of hand definition moved After's cameras by almost 9°. Drop those two terms, keep upper arm, forearm, shoulder width and torso, and keep the hand points in the reprojection term only. CasCalib likewise excludes arm and head points from its final adjustment ([CasCalib](https://arxiv.org/html/2405.06845v1)). Second, scale residuals per camera by the measured noise. Huber's `f_scale = 2 px` means different things at 480 px and 1080 px widths, and the noise model already holds per-view, per-joint σ. Third, report a profile of the bundle-adjustment cost over the free 480p focal, and over the iPhone crop factor, together with the Gauss–Newton condition number. If the profile is flat over more than ±10%, the prior is doing the work and the report must say so. Fourth, look for independent checks that never touch the FBX. Room lines can give a vanishing-point focal for each view. Person-masked median background frames can be matched with SuperPoint+LightGlue or MASt3R, whose relative-pose AUC@10° of about 76 on MegaDepth clearly beats older matchers ([CoMatcher evaluation](https://arxiv.org/pdf/2504.01872); [MASt3R](https://arxiv.org/pdf/2406.09756)). Fifty or more spread inliers would sharpen the rotation and baseline. They would not resolve the focal degeneracy, which is a property of the camera layout, and the 480p frame's compression and the limited background overlap at a 50–65° yaw make the test a gamble. Allow one day for it, as a feasibility test.

Two uses of the FBX in calibration must stay excluded: Procrustes-fitting FBX joints to the keypoints, and choosing a focal that makes the reconstruction look like the suit. Both condition the calibration on the outcome. Taking FBX segment-length ratios as a bone prior is borderline. Angles do not depend on lengths directly, but a length prior moves the cameras and so the depth shear. The cleaner role for the FBX is a held-out diagnostic computed after calibration, such as suit-versus-video segment-length ratios in the rest pose.

## Software can add pixels to the 1080p hands, but shoulder elevation needs a definition decision

Hand keypoints are RTMW's weakest output: hand AP is 66.3 against 76.1 for the body, and the authors attribute the gap to how few input pixels a hand receives ([RTMW](https://arxiv.org/html/2407.08634)). The pipeline warps the person box to 384×288. In a 1080p portrait frame that means about 2.4–2.6× downsampling, so a hand about 45 px wide reaches the model at about 18 px. In the 480p view the box is close to native size, so a crop adds no new pixels there (in-house). A second stage that runs RTMPose-m hand (hand5 checkpoint, 256×256, PCK@0.2 0.815 on COCO-WholeBody-Hand; [MMPose hand README](https://cdn05042023.gitlink.org.cn/OpenMMLab/mmpose/src/branch/main/configs/hand_2d_keypoint/rtmpose/README.md)) on 1.5–2× crops of the original frame recovers those pixels. It loads through rtmlib on CPU ([rtmlib](https://pypi.org/project/rtmlib/0.0.14/)). The gain therefore lands in the 1080p view, which is After's side view (index-point σ 11.4 px) and Action's front view (11.3 px). It cannot rescue Action's 480p hands, and super-resolution will not either. SR mainly helps detect very small subjects and hurts as they grow ([Hardy et al.](https://arxiv.org/abs/2107.02108v2)), and it risks hallucinating knuckle structure. Use the hand model only for the four MCPs, keep the RTMW body wrist so the forearm vector does not change definition, re-run the same five augmentations on the crop, and bump `CACHE_VERSION`. Pointing error scales with σ/L, so halving a view's knuckle noise roughly halves that view's share of wrist-angle noise. That gain has to be measured, not assumed.

Triangulation and the noise model come next. `triangulate` weights each view by detector confidence, which is poorly calibrated as an error estimate ([Gu et al., ICML 2024](https://arxiv.org/html/2311.17105v1)), and its algebraic DLT error treats a 480p pixel like a 1080p pixel. Replace it with per-view, per-joint inverse-variance weights from the measured noise. Better still, minimise Mahalanobis reprojection error per point, and flag frames whose epipolar residual exceeds a χ² bound instead of dropping them silently. With two views, a bad point can be detected but not attributed to either view. Fit a per-frame σ as a function of confidence on still frames, with a floor of 1–2 px. Without such a floor, a biomechanical fitting pipeline's error model became badly overconfident ([Cotton group, arXiv 2502.06486](https://arxiv.org/html/2502.06486v1)). Keep the 6 Hz zero-lag Butterworth. One-euro and acceleration-minimising filters blunt range of motion ([Pose2Sim](https://github.com/perfanalytics/pose2sim)), and learned smoothers such as SmoothNet ([ECCV 2022](https://www.ecva.net/papers/eccv_2022/papers_ECCV/html/1848_ECCV_2022_paper.php)) are trained on motion unlike fast signing and would smooth video toward an already smooth suit.

The suit side needs no glove check for the wrist. The `Hand*1` bone heads are children of the `Hand` bone, so the FBX knuckle centre is by construction a rigid point on the hand segment, whatever the fingers do (in-house, from the skeleton hierarchy). The FBX wrist angle is therefore "hand-segment orientation", and the report should word it that way.

Shoulder elevation is a different kind of problem. Video read After's right shoulder 13–15° low with the arm up, and Action's left shoulder 20–24° low for 42% of the sign. Markerless shoulder points sit 24–34 mm from marker-based centres ([Needham et al. 2021](https://pmc.ncbi.nlm.nih.gov/articles/PMC8526586/)), and shoulder-angle errors from landmark offsets grow sharply near 90° of elevation ([UTS marker-offset study](https://opus.cloud1.lib.uts.edu.au/bitstream/10453/117406/1/Shoulder%20joint%20angle%20errors%20caused%20by%20marker%20offset.pdf)). A shoulder keypoint that rides up the visible contour by d, on an upper arm of length ℓ, lowers measured elevation by about atan(d/ℓ): **10° for 5 cm and 20° for 10 cm** (in-house). The pre-sign-hold offset cannot remove a gap that is near zero at rest and grows with elevation. Software offers three cause-level options, and none of them can be tuned on these takes. The first builds an acromion-like virtual marker on the FBX: a point on the clavicle (`LeftShoulder`) segment at an anatomically fixed fraction. This requires adding the clavicle bones to `EXTRA_BONES`, and first an FBX-internal check of whether Rokoko actually rotates the clavicle. The second shifts the video shoulder point by an anatomically fixed fraction of shoulder width in the thorax frame. The third redefines elevation against a thorax axis built from the hips and a shoulder midpoint frozen in the thorax frame at the hold, so a shrug no longer moves the humeral origin. All three change the claim from humeral elevation to an agreed proxy, and that must be said. An OpenCap-style learned marker enhancer is evidence that point semantics matter, since it cut kinematic error by 4.2° on average. It is not a tool for this problem: it needs paired training data, and its first version generalised poorly to unseen movements ([Marker Data Enhancement](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12198419/)). Fitting offset and gain on the tested frames is ruled out entirely, Deming or otherwise. By construction it absorbs real disagreement, leaving only an "agreement after recalibration" claim, and Deming intervals are known to be too narrow ([valytics vignette](https://ftp.fau.de/cran/web/packages/valytics/vignettes/deming-regression.html)).

## The implementation order puts measurement before uncertainty, and definitions last

The order follows three rules. A change goes earlier when its correctness can be checked without the suit–video difference, using internal diagnostics or a simulation with known truth. It goes later when it changes what is being claimed. Honest uncertainty propagation comes before any precision gain, so that no precision gain is ever reported against an over-tight bound. Each step should land as a separate commit with its own regression test, in line with the project's conventions.

Some options are deliberately left off the list. A whole-take fit with constant bone lengths, SMPL-X or biomechanical model fitting, and ensembles with ViTPose or Sapiens are all high effort, and their gains are uncertain or move bias into the model's own joint definitions ([Cotton group follow-up](https://arxiv.org/pdf/2601.22412)). Dynamic time warping, fitting offset and gain on the sign window, Procrustes calibration to the FBX, and choosing any variant by its suit agreement are excluded outright. Internal metrics have a known limit as selection criteria. Reprojection-based scores can barely change between algorithms that differ downstream ([arXiv 2303.02413](https://arxiv.org/pdf/2303.02413)), and a semantic offset is geometrically self-consistent, so no internal metric can see it. Step 0's simulator is what turns "lower reprojection error" into "lower angle error" for this pipeline. Without it, the selection rule is an assumption.

Expectations should be realistic. Steps 2–5 will move the cameras, and a camera move pushed After's right elbow from a comfortable to a marginal pass once before. Step 8 will widen every bound. A re-analysis may therefore confirm fewer angles than the current exploratory runs, and that outcome must be reported as readily as a gain. Several things no software can change: Action has no pre-sign hold, so the pre-registered offset rule still refuses it. Its 480p side view keeps its few hand pixels. And the 50–65° baselines keep about 1.2–1.55× the depth noise of a 90° layout (in-house, from √(1 + cos²θ)/sin θ).

## Already-seen takes allow only a blinded, exploratory re-analysis

Both takes, their offsets and their pass/fail pattern are known, so no new code can make After or Action confirmatory. Blind analysis exists to keep analysts from steering toward an answer they can see ([Roodman 2003](https://arxiv.org/abs/physics/0312102); [MacCoun & Perlmutter, Nature 2015](https://www.nature.com/articles/526187a.pdf)). Preregistration of secondary analyses asks authors to declare what they already know, because prior knowledge of the data biases the choices that follow ([van den Akker et al., Meta-Psychology](https://open.lnu.se/index.php/metapsychology/article/view/2625); [Baldwin et al.](https://pmc.ncbi.nlm.nih.gov/articles/PMC8791887/)). Partial blinding still limits new forking paths. Its value is not in making the result confirmatory but in making the re-analysis credible as exploration.

| Step | What to do | Why |
|---|---|---|

| Internal-only selection | Develop and choose settings with the blinding harness, which shows reprojection error, held-out reprojection, upper-arm and forearm length CV, multi-start agreement, lag signal spread, TTA spread and still-hold jitter, and never the suit–video differences. Fix one lexicographic rule in advance, e.g. "lowest held-out reprojection error subject to forearm CV < x%" | Keeps tuning from being steered toward a pass; definition choices (step 12) come from anatomy only |
| Simulation gate | Run every new step inside the at-margin simulation (true RMS at 15°, about 100 takes per row, ≤ 5 parallel processes with `OMP_NUM_THREADS=1`); drop any step whose false-equivalence rate exceeds 5% | Type I error is the one property the takes cannot check |
| Freeze | Commit the code and a dated re-analysis plan (in `equivalence_margins.json` or beside it) naming the primary exploratory specification and every variant; record the commit hash | Fixes the analysis before the answer is visible |
| Unblind once | Report the primary exploratory specification and a full multiverse table: every reasonable combination of calibration, sync, hand-model, offset-rule and definition variants, with each one's own Monte Carlo RMS upper bound and the fraction of specifications passing per angle | Multiverse and specification-curve reporting show fragility instead of hiding it ([Steegen et al. 2016](https://errorstatistics.com/wp-content/uploads/2016/10/steegen-et-al-2016-increasing-transparency.pdf); [Simonsohn et al. 2020](https://link.springer.com/article/10.1038/s41562-020-0912-z)) |
| Label | Every claim reads "exploratory: data previously analysed"; anything changed after unblinding is "post-blind" | Post-blind analyses are less credible and must say so |

Four further rules hold throughout. **The ±15° margin is never widened**, for any angle, and no angle is dropped. The pre-registered fixed sequence stays the headline. Fallback, Holm or a Bretz graphical procedure ([Bretz et al.](https://arxiv.org/pdf/1908.10262)) may appear only as labelled exploratory columns, because switching procedure after seeing that an early group failed is a data-dependent choice that breaks familywise control. Any fitted parameter, whether an offset, a virtual-marker length set from a static geometric quantity, or a lag, is re-estimated inside every Monte Carlo draw. And "tune on one take, confirm on the other" is not available, because both takes have been seen. The weaker version is still worth reporting: develop any fitted correction on Action, which is exploratory anyway, then apply it frozen to After and call the result cross-validated, not confirmatory. A frozen pipeline becomes confirmatory only for takes recorded after its commit, which lies outside the current no-new-recordings constraint.

### Most of the earlier recording advice is ruled out, and seven ideas survive as code

The earlier report on improving single-take equivalence relied mostly on the recording protocol, and most of that is ruled out once the inputs are frozen. Measured per-phone intrinsics from a chessboard, a printed board for extrinsics in each take, a 70–90° phone layout, both phones at 1080p and 60 fps with a fast shutter, stabilisation off and tighter framing, a calibration block (arm-raised holds, slow elbow bend, wrist sweep) for fitting offset and gain, slap events before and after the sign, RecSync or an LED clock, a third phone, suit preparation against magnetic disturbance, a dedicated noise recording, multi-take and multi-sign replication, and a pre-sign hold for Action all need new footage or new suit data. One borderline case deserves a question to the user rather than a ruling. Pose2Sim's scene calibration uses ten or more tape-measured room points visible in both videos and works on unsynchronised cameras ([Pose2Sim](https://github.com/perfanalytics/pose2sim)). If the room is unchanged, that adds measurements without re-recording anything. A strict reading of "only the code may change" excludes it, and it would be the strongest calibration fix available.

Seven ideas survive in software form. Timestamp verification is now done. Continuous spline sync on the 60 fps base, the multi-signal FBX lag and lag draws in the Monte Carlo carry over unchanged, as steps 2, 3, 7 and 8. Board calibration survives as its software substitute: metadata-bounded iPhone focal, a calibration decoupled from the hand point, and optional background matches (steps 4–6). The shoulder-semantics fix survives as anatomically fixed virtual markers or a frozen thorax axis (step 12), without the calibration block's fitted gain. The second-stage hand model and noise-weighted fusion survive as steps 9–10, with the caveat that they help only the 1080p view. Hand-labelled motion-time frames survive as step 11, since labelling existing frames records nothing new. The graphical or fallback multiplicity procedure survives, but only as an exploratory column on these takes and a commitment for future ones.

## Conclusion

The headline result of this round is that the instability the project has attributed to two-view geometry in general has a narrower cause. The pipeline is solving for a focal length the phone already reports. Bounding the iPhone focal turns a singular two-unknown problem into a one-unknown problem the literature calls well-posed for this layout, and that change costs hours. Its value is the same as board calibration's would have been: a take's result stops depending on which keypoint defines the hand. The second lesson runs against intuition. The most important near-term software change, putting lag and focal uncertainty into the Monte Carlo, makes every bound wider. A pipeline that cannot show how much of its margin is spent on sync and calibration cannot be trusted to report a pass.

What software cannot do is as important. It cannot create the missing pre-sign hold in Action, add pixels the 480p hands never had, or turn already-seen takes into confirmatory evidence. The shoulder-elevation gap will not yield to better numerics, because it is a disagreement about what "shoulder" means. Fixing it is a definitional commitment that must be made from anatomy, written down, and frozen before anyone looks. Run that way, the re-analysis will show which of the current passes survive honest uncertainty, and it will leave a locked pipeline ready for the first take recorded after the commit.
